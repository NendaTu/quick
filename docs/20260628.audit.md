# Scalper System Audit Report - 20260628

This document provides a thorough diagnostic of the trading application, focusing on Code & Structure and Technical Analysis Tools.

## 1. Code & Structure

### Finding 1: Trade Count and Win-Rate Inflation
- **Location**: `engine.py`, `_report_exit`
- **Description**: `self.total_trades` is incremented on every call to `_report_exit`, regardless of whether it's a partial or full exit. In `BE+TP1+TP2` strategy, a single trade hitting both targets will count as 2 trades and 2 wins.
- **Impact**: Success metrics (Win Rate, Total Trades) are artificially inflated. A 60% win rate might actually be 45% if successful trades are counted twice.
- **Recommendation**: Only increment `total_trades` when `is_partial` is `False`.

### Finding 2: Incomplete Concurrency Limit Enforcement
- **Location**: `engine.py`, `_trading_loop`
- **Description**: The check `if len(self.open_positions) < MAX_CONCURRENT_POSITIONS` ignores `self.pending_entries`. If 100 limit orders are pending, the bot will still try to enter new trades.
- **Impact**: The bot can significantly exceed the `MAX_CONCURRENT_POSITIONS` limit, leading to over-exposure and potential margin liquidation.
- **Recommendation**: Update the check to `if (len(self.open_positions) + len(self.pending_entries)) < MAX_CONCURRENT_POSITIONS`.

### Finding 3: Margin Check Logic Gaps
- **Location**: `simulator.py`, `place_trade_oco`
- **Description**: For market orders, `required_margin` is calculated and checked against `available_balance`, but the immediate `fee` deduction that happens in `_execute_entry_direct` is not pre-calculated or reserved.
- **Impact**: In low-balance scenarios, a market order might be approved but then drive the equity below the required margin for the next order or even into a negative available balance immediately after fill.
- **Recommendation**: Include estimated entry fees in the `required_margin` check during the approval phase.

### Finding 4: Limit-Chase Margin Re-verification
- **Location**: `simulator.py`, `_process_orders` (entry_timeout logic)
- **Description**: When a limit entry times out and is converted to a "market-ish" fill, the price might be significantly different (higher for buy, lower for sell) than the originally reserved price. There is no re-verification of margin availability at the new fill price.
- **Impact**: The bot could enter a position with higher margin requirements than available, causing a mismatch in simulated vs real-world balance behavior.
- **Recommendation**: Perform a quick margin check before `_execute_entry_direct` in the timeout handler.

### Finding 5: Real-time Feature Calculation Bottleneck
- **Location**: `simulator.py`, `get_features` and `engine.py`, `_trading_loop`
- **Description**: The system calculates expensive technical patterns (FVG, OB, Liquidity, etc.) for every enabled asset on every update tick (0.1s - 0.2s). Most of these patterns only change on candle close.
- **Impact**: Severe CPU waste and potential lag in the trading loop. On a MacBook M3 Pro, this might be manageable for 10 assets, but will scale poorly to 250 assets.
- **Recommendation**: Implement a caching layer or only update pattern features on candle close or every X ticks.

### Finding 6: Missing Signal Collision Prevention in Burst
- **Location**: `engine.py`, `_trading_loop`
- **Description**: The loop iterates over assets. If two signals are generated for the same asset in different directions (e.g., a "Long" score and a "Short" imbalance), there's no atomic check between the decision and the `place_trade_oco` call to prevent both from firing.
- **Impact**: While `_asset_is_tradable` checks `pending_entries`, it doesn't prevent a signal from the current tick being processed if the asset was clear at the start of the loop.
- **Recommendation**: Re-verify `_asset_is_tradable` immediately before `place_trade_oco`.

## 2. Technical Analysis Tools

### Finding 7: Look-ahead Bias Risk in Break Signals
- **Location**: `ta/patterns/structure.py`, `identify_structure`
- **Description**: The logic uses `ohlcv[-1]` (the current candle) to detect BOS/MSS. While this allows for "real-time" entry, it uses the high/low of an unclosed candle. If the price spikes through a level and retraces, a signal is fired even if the candle ultimately closes below the level (a "fakeout").
- **Impact**: High frequency of "false break" entries which are statistically lower probability than confirmed candle-close breaks.
- **Recommendation**: Add a `REQUIRE_CLOSE` toggle to confirm breaks only on candle close, or at least require price to stay beyond the level for X ticks.

### Finding 8: RRR Synchronization Math Inconsistency
- **Location**: `models.py`, `predict`
- **Description**: The calculation for `tp_move_from_roe` uses `(TARGET_NET_ROE / max_lev)`. However, `TARGET_NET_ROE` is defined in `config.py` as `0.20` (20%). If `max_lev` is 20, the move is `0.01` (1%). This is correct, but the log comments in `models.py` (e.g. "relaxed target 3% instead of 5%") imply a confusion between decimal ROE and percentage ROE.
- **Impact**: Confusion in strategy tuning; actual targets might be 10x smaller or larger than intended if the user inputs `5` instead of `0.05`.
- **Recommendation**: Standardize all config inputs to either decimal or percentage and add assertions.

### Finding 9: Fair Value Gap State Monotonicity
- **Location**: `ta/patterns/fvg.py`
- **Description**: The state of an FVG transitions from `unfilled` to `mitigated` to `engaged` to `inverted`. However, the current logic scans the *entire* post-gap history on every tick.
- **Impact**: Redundant calculation. Once a gap is `inverted`, it should be removed from the active scan list.
- **Recommendation**: Mark `inverted` gaps as terminal and stop scanning them.

### Finding 10: Institutional Delivery Model (IDM) Precision
- **Location**: `ta/patterns/idm.py`
- **Description**: IDM is defined as a sweep occurring within a Killzone. However, the current implementation doesn't check if the sweep *happened* within the window, only if an IDM "is active" if a sweep *exists* and we *are* in a window.
- **Impact**: A sweep from 4 hours ago (outside the London Killzone) would trigger an IDM "Bullish" signal if the bot happens to be in the London window.
- **Recommendation**: Ensure the `sweep_detected` timestamp is within the `active_kz` window.

### Finding 11: BTC Confluence Lag
- **Location**: `simulator.py`, `get_features`
- **Description**: BTC confluence is calculated using `confluence_history`. This is updated in `_update_candles`. If the bot is running on a 1m timeframe, the `btc_15m` change only updates every minute when a new candle is formed, or on every tick if the current price is used.
- **Impact**: The `btc_15m` feature reflects the change from the *previous* 15m candle close to the *current* price. This is correct but might be noisy compared to 15m interval checks.
- **Recommendation**: Clarify if BTC confluence should be "Last Closed Candle" vs "Real-time Move". Current implementation is "Real-time Move" which is more reactive but more prone to noise.
