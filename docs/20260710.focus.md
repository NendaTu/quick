# Focus Log - 2026-07-10

## Focus Areas & Key Findings

### 1. P&L Discrepancy (Issue 1)
- **Problem**: Live trades (e.g., TKOUSDT, ALLOUSDT) were closing at a loss on the exchange, but the application registered them as profitable.
- **Root Cause**: The position reconciliation code in `Engine._sync_exchange_state()` was detecting gone positions and calculating P&L using `self.exchange.last_price` at the moment of sync. This price is highly volatile, suffers from time-delay, and does not represent actual execution fill prices. Additionally, entry and exit fees were completely omitted.
- **Decision**: Update `_sync_exchange_state()` to fetch the exact closed position details via `/api/v2/mix/position/history-position` and `/api/v2/mix/order/fills`. Implement a precise theoretical fallback that incorporates Maker (0.0002) and Taker (0.0006) rates.
- **Confirmation**: Added test suite `tools/test_order_pnl_reconciliation.py` which passes successfully, validating correct mapping, retrieval, and fallback computations.

### 2. Signal-to-Trade Conversion Failure (Issue 2)
- **Problem**: Entry signals are written to logs, but no actual orders are filled.
- **Root Cause**: Placed limit entry orders were never registered in `self.pending_orders`. Thus, the limit order chase and timeout cancel queue was always empty. The engine's `pending_entries` would keep the asset locked forever, blocking all subsequent trades.
- **Decision**: Update `BitgetExchange.place_order` to register limit entries into `self.pending_orders` with the exchange `orderId`.
- **Confirmation**: Tested via `tools/test_order_pnl_reconciliation.py`.

### 3. Trade Frequency Gap (Issue 3)
- **Problem**: Live frequency is far below backtest frequency.
- **Root Cause**: Directly caused by the limit order tracking bug above. Once a limit entry was placed, the asset was locked indefinitely, preventing any further trades from being attempted on that asset.
- **Decision**: Fixed by enabling the timeout chase queue, which cancels stale limits after `LIMIT_CHASE_TIMEOUT` and unlocks the asset.

### 4. Leverage Configuration (Issue A)
- **Problem**: Trades were opening with 10x leverage instead of maximum available leverage, and risk wasn't strictly configured in Isolated Margin.
- **Root Cause**: There were no methods in the client to set leverage and margin mode, meaning Bitget used default values.
- **Decision**: Implemented `set_leverage` (`/api/v2/mix/account/set-leverage`) and `set_margin_mode` (`/api/v2/mix/account/set-margin-mode`) on `BitGetClient` and `BitgetExchange`. Enforced them dynamically right before placing an order in `place_order`.
- **Confirmation**: Successfully verified and covered under unit testing.

### 5. Split-Target Exit Trigger Orders (Issue B)
- **Problem**: Necessary exit trigger orders were missing at the time of entry, and only partial stop losses were visible on-exchange.
- **Root Cause**: Bitget order presets only allow a single TP/SL target. Split-target strategies (TP1/TP2) could not post separate trigger orders upon order entry, and there was no position auditing system to ensure missing triggers were posted.
- **Decision**: Implemented `place_tpsl_order` (`/api/v2/mix/order/place-tpsl-order`) and `get_open_tpsl_orders` (`/api/v2/mix/order/orders-plan-pending`). Added a dynamic position audit inside `_sync_exchange_state()` to detect open positions and post missing TP1/TP2 trigger orders on-exchange automatically.
- **Confirmation**: Verified and validated through comprehensive tests.

### 6. Backtest Engine Look-Ahead Bias and Mode Dependency
- **Problem**: Extreme discrepancy between backtest performance and live trading, and backtest fails to run or complete if `.env` MODE is set to `"live"` or `"demo"`.
- **Root Cause**:
  1. A major look-ahead bias bug existed in `backtest.py`'s multi-timeframe synchronization loop. Multi-timeframe candles (15m, 1H, 4H, etc.) were appended to history as soon as the start of their period was reached rather than at their actual closed time, granting the strategies up to several hours of future visibility.
  2. `Engine` instantiation in `backtest.py` did not pass a forced mode, meaning it read `config.MODE` from `.env`. If it was live/demo, it initiated real exchange connections and balance fetches instead of simulation mode, failing if private keys were missing or if it couldn't connect to private WebSockets.
- **Decision**:
  1. Fixed synchronization timing: A candle of timeframe `t` is only appended once `current_ts` reaches or exceeds `ts + TF_SECONDS[t]`, completely eliminating look-ahead bias.
  2. Forced `mode="paper"` on `Engine` in `backtest.py`, ensuring it runs strictly in simulation mode under any `.env` configuration.
  3. Hardened `BitGetClient` to support fetching public data (candles, contracts) without requiring any private keys or raising ValueError.
- **Confirmation**: Verified by running backtest runs successfully under different mode overrides, generating correct results and tables.

### 7. Dynamic Safe Leverage Capping (Premature Liquidation Risk)
- **Problem**: Enforcing `RISK_PER_TRADE` means the Stop Loss represents the maximum amount that can be lost. Under high or blind contract leverage, the position can liquidate before the Stop Loss is hit.
- **Root Cause**: If the distance to the Stop Loss exceeds the liquidation distance (determined by leverage), the exchange will liquidate the position in Isolated Margin before the SL price is reached.
- **Decision**: Implemented dynamic safe leverage capping inside `BitgetExchange.place_order` right before placing a trade. We compute `max_safe_leverage = int(0.9 / (abs(price - sl_price) / price))`, capping our applied leverage so that the liquidation price is guaranteed to be wider than the Stop Loss price.
- **Confirmation**: Verified and confirmed to perfectly respect the dynamic risk and SL parameters.
