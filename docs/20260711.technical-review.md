## Detailed Codebase Audit Findings

### 1. Engine Core (`engine/core.py`)
- **State Reconciliation**: The startup synchronization loop (`_sync_exchange_state()`) has been fully validated. It reconciles open positions, ensures Isolated Margin is applied, retrieves actual closed trade history/fills, and automatically posts missing trigger orders (TP1/TP2) on the exchange.
- **Graceful Shutdown**: The bot captures shutdown signals (`SIGINT`, `SIGTERM`) and waits for open positions to be settled before stopping completely.
- **Metrics Log**: Evaluated signals are cleanly logged to `docs/temp/[timestamp].metrics-log.txt`, capturing the exact strategy ID and more than 40 indicators for complete auditing transparency.

### 2. Exchanges (`engine/exchanges/`)
- **Dual-Client Architecture**: Maintains an elegant separation between `data_client` (Live API key for public market data, preventing demo key 40099 exceptions) and `client_exec` (Live or Demo keys for private execution).
- **Rate Limiting**: Enforced safely at 10 RPS with 5 concurrent requests (98% safety cap on `RateLimiter`), preventing any 429 rate limit issues during long background warm-ups.
- **Symbol Mapping**: Automated symbol conversion maps canonical tickers (e.g., BTCUSDT) to Demo environment symbols (e.g., SBTCUSDT) cleanly.

### 3. Strategy Orchestration (`strategies/sweeps/`)
- All sweep strategies strictly respect `config.REINVESTMENT_PERCENTAGE` for mathematical compounding.
- The 1-hour cooldown resets strategies back to `IDLE` from `COMPLETED` successfully, allowing compounding loops to recur safely.
- **Minimum Distance Guards**: All strategies successfully implement a minimum SL distance of 0.1% to prevent zero-width fee traps.

### 4. Technical Analysis (`ta/`)
- **Look-Ahead Bias Elimination**: Multi-timeframe candle synchronization in `backtest.py` strictly appends candle history only after their period has closed (`current_ts >= ts + TF_SECONDS[t]`).
- **Cache Isolation**: The swing high/low detector (`ta/patterns/swings.py`) incorporates starting and ending close prices into the cache key, mathematically preventing cross-symbol target contamination.
- **Closed Candle Evaluation**: Signals are generated strictly on closed candles (`ohlcv[:-1]`) to prevent repainting.

## Modularity & Single-Responsibility Findings

### Finding 1: God-Object Concerns in `Simulator` and `BitgetExchange`
- **Violation**: The `Simulator` class is responsible for multiple concerns: (1) simulated matching engine execution, (2) technical indicator feature extraction, and (3) historical data acquisition. `BitgetExchange` inherits from `Simulator`, mixing live REST API data polling, real WebSocket feed parsing, and virtual simulation state.
- **Origin**: The system was designed around a simulation-first methodology. Instead of keeping exchange interactions clean and modular, features were added to the simulator, and the live exchange driver was designed as a direct subclass.
- **Cost**: Unit-testing is difficult without comprehensive mocks, and changing the simulation engine risk/fee model risks breaking the live execution pipeline.
- **Recommendation**: Decouple the Technical Indicator Feature Extractor into a pure stateless module (`ta/features.py`). Extract the simulator matching engine into an isolated class (`engine/simulation.py` or a dedicated matching runner), making `BitgetExchange` a pure adapter implementing a clean `BaseExchange` interface.

### Finding 2: Tight Coupling of Configuration Loader
- **Violation**: `config.py` acts as both a static settings file and a global variable pool. This global state is imported directly everywhere and modified dynamically during backtests (`importlib.reload(config)`).
- **Origin**: Quick prototyping relied on globally accessible settings.
- **Cost**: High risk of thread-safety issues, global variable pollution, and confusing reload/override behavior during portfolio backtesting.
- **Recommendation**: Load settings into a dedicated, immutable configuration class instance (`ConfigContext`) passed cleanly to engine and strategy constructors.

### Finding 3: Mix of Signal Evaluation and Persistence in `Engine._trading_loop`
- **Violation**: `Engine._trading_loop()` is responsible for: (1) calculating features, (2) evaluating active strategy signals, (3) routing entries, (4) local order state persistence, and (5) writing metrics logs.
- **Origin**: Added sequentially in development cycles without refactoring boundaries.
- **Cost**: Signal evaluation logic is tightly coupled with file I/O and state registration, making dry-runs or strategy auditing difficult.
- **Recommendation**: Extract signal evaluation into an isolated `SignalEvaluator` class, keeping the `Engine` loop clean and focused on task scheduling and order dispatching.
