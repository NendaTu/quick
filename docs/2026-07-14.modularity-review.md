# Single-Concern and Modularity Report — 2026-07-14

This report reviews the codebase's architecture, identifying modularity and single-responsibility violations, and suggesting refactoring opportunities.

---

## Architectural Summary: Most Problematic Files
Based on our architectural scan, the following files contain the highest concentration of conflated concerns and duplicated logic, making them prime candidates for refactoring:
1. **`strategies/sweeps/*`**: Duplicated code for precision formatting, order sizing rounding, and minimum contract checks.
2. **`tools/trading_utils.py`**: Direct tight coupling to the global `config` module, preventing process-level config isolation during multi-threaded/A/B comparison runs.
3. **`simulator.py`**: Contains both `DataAcquisitionManager` and `Simulator` within the same file, crossing database persistence and order matching boundaries.

---

## Specific Modularity Findings

### **1. Duplicated Sizing & Rounding Rules**
- **Location**:
  - `strategies/sweeps/killzone/killzone_sweep.1.mustafa.py` (Lines 362-383)
  - `strategies/sweeps/killzone/killzone_sweep_overnight.1.mustafa.py` (Lines 347-368)
  - `strategies/sweeps/range/range_sweep_ATR.1.mustafa.py` (Lines 355-376)
- **Violation Type**: Logic Duplication
- **Description**: Each strategy independently queries the exchange contract specifications, resolves `pricePlace` / `quantityPlace`, calculates the minimum trade value based on `minTradeUSDT`, floors the quantity to prevent exceeding margin limits, and performs rounding.
- **Why it happened**: Strategies were developed independently as standalone files to facilitate rapid testing of unique signal conditions.
- **What correct looks like**: Extract this logic into a unified helper function inside `tools/trading_utils.py` (e.g. `format_order_quantity_and_price(qty, entry_price, contract_specs)`).

---

### **2. Duplicated Fee Selection Logic**
- **Location**:
  - `engine/exchanges/bitget.py` (Lines 116-117)
  - `simulator.py` (Lines 784-785)
  - `models.py` (Lines 173-175)
- **Violation Type**: Logic Duplication
- **Description**: The rule that determines whether to apply the Maker Fee (if the order type is limit) or Taker Fee (if the order type is market) is defined separately inside the Live Exchange interface, the Paper matching engine, and the scoring Models.
- **Why it happened**: Parity between simulated paper mode and real exchange execution was implemented by copying the fee determination logic.
- **What correct looks like**: Centralize this choice inside `tools/trading_utils.py` (e.g. `get_fee_rate(order_type, is_limit)`).

---

### **3. Global Config Dependency Coupling**
- **Location**: `tools/trading_utils.py` (All functions)
- **Violation Type**: Inappropriate Dependency / Scattered Configuration
- **Description**: All calculations inside `tools/trading_utils.py` (such as `calculate_fees`, `calculate_roe`, and `calculate_position_size`) import and access the global `config` module directly. This violates the `ConfigContext` dependency injection pattern introduced for multi-threaded/variant runs.
- **Why it happened**: `trading_utils.py` was written early in development before `ConfigContext` was introduced as a standard.
- **What correct looks like**: Allow all utility functions to accept an optional `config` parameter (defaulting to the global `config` module).

---

### **4. Conflated Responsibilities in `simulator.py`**
- **Location**: `simulator.py`
- **Violation Type**: Single Responsibility Violation
- **Description**: `simulator.py` defines `DataAcquisitionManager` (which handles database caching and downloading historical candle data) and `Simulator` (which simulates order book matching and virtual trade executions) in the same file.
- **Why it happened**: This was done to group all paper trading logic in a single file.
- **What correct looks like**: Separate the historical data acquisition manager into its own file (e.g. `engine/acquisition.py`) and keep `simulator.py` purely dedicated to order execution matching.
