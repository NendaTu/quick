## 1. Historical and Warmup Data Acquisition Pipeline [RESOLVED]

### Diagnosis of Slowdown
The investigation into why acquisition moved from "minutes" to "hours" has yielded the following findings:

1.  **Strict Global Rate Limiting:** Both `tools/downloader.py` and `backtest.py` utilize a `RateLimiter` class that enforces a strict global RPS (Requests Per Second) cap. In `downloader.py`, this is set to **8 RPS**. In `backtest.py`, it is **15 RPS**.
    *   **Impact:** Even for a modest 1-month request of 1m data (approx 44,000 candles), Bitget's 200-candle limit requires 220 requests. Across 250 assets, this is 55,000 requests. At 8 RPS, this takes **~1.9 hours** just for one timeframe.
2.  **Sequential Gap Filling:** The current implementation iterates through `db.get_data_gaps()` results one by one. If an asset has multiple small "holes" (e.g., due to previous interruptions), the system makes a full round-trip API call for every 1-candle gap, ignoring that the API returns up to 200 candles which could have filled the next dozen gaps in one go.
3.  **Low Concurrency:** `CONCURRENCY_LIMIT` is set to **2** in `downloader.py` and **5** in `backtest.py`. This is extremely low for asynchronous I/O and fails to saturate even the conservative RPS limits, adding significant "idle" time between requests.
4.  **API Limit Constraint:** My testing confirmed that Bitget V2 strictly enforces a `limit=200` for `history-candles`. Any attempt to fetch more (e.g., 500 or 1000) results in a `40053` error.

### Resolution
- **Asynchronous Batching:** Implemented "fetch_chunk" parallelization in `tools/downloader.py` and `backtest.py`.
- **RPS Optimization:** Tuned `DEFAULT_RPS` to 10 and `DEFAULT_CONCURRENCY` to 5 for high-stability historical runs.
- **Gap Aggregation:** Implemented "Gap Merging" in `database.py` with a 10-candle threshold to minimize round-trips.
- **Robust Backoff:** Centralized jittered exponential backoff and incremental retry delays in `BitGetClient`.

## 2. Strategy Discovery & Loading [RESOLVED]

### Findings
- **Location:** `backtest.py:find_strategy_file`
- **Issue:** The strategy discovery logic in `backtest.py` does not search the `strategies/` directory recursively. While `load_strategy` in `main.py` is recursive, the pre-check in `backtest.py` fails to find strategies in subdirectories (e.g., `sweeps/killzone/`).
- **Issue:** The fuzzy matching logic is sub-optimal, sometimes matching partial filenames across different directories.

### Resolution
- **Recursive Discovery:** Refactored `backtest.py:find_strategy_file` to search the `strategies/` directory recursively, syncing it with the `main.py` loader logic.
