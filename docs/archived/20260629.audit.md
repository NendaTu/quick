# Audit Report - June 29, 2026

**Auditor:** Jules, Senior Software Architect
**Scope:** Bitget USDT-M Futures Trading Bot
**Context:** High-frequency, high-win-rate compounding (5% ROE per trade goal).

---

## 1. Code & Structure

### [CS-001] Expensive Feature Calculation in Trading Loop
- **Location:** `engine.py`, `_trading_loop` (Lines 216-250)
- **Description:** The engine iterates through all enabled assets (up to 250) on every tick (0.2s) to calculate technical features. While there is a `_feature_cache` in `Simulator`, the `Engine` still calls `self.exchange.get_features(sym)` for every asset where a position isn't full.
- **Impact:** High CPU usage and potential loop lag as the number of assets increases. At 250 assets, calculating complex patterns (FVG, OB, Structure) every 200ms is inefficient.
- **Recommendation:** Implement a more robust "Signal Dirty" flag. Only recalculate expensive patterns when a new candle closes. Real-time metrics (Spread, Imbalance) should be separated from slow patterns.

### [CS-002] Fragile Concurrency in Position Tracking
- **Location:** `engine.py` (`pending_entries`, `open_positions`) and `simulator.py` (`positions`, `pending_orders`)
- **Description:** There is redundant and potentially desynchronized tracking of positions between the `Engine` and the `Simulator`. `Engine._report_entry` is called by the `Simulator` after a fill, but `Engine` also pre-emptively adds to `open_positions` for market orders (Line 318).
- **Impact:** Potential for "Ghost Positions" or double-counting if an entry fails at the exchange level but is registered locally, or if the callback is delayed.
- **Recommendation:** Centralize position state. The `Engine` should treat the `Simulator/Exchange` as the single source of truth and only update its local state based on confirmed execution callbacks.

### [CS-003] Decimal vs. Percentage Ambiguity in Config
- **Location:** `config.py` (`TARGET_NET_ROE`, `RISK_PER_TRADE`, `TOTAL_ROI_LIMIT`)
- **Description:** Configuration values use decimals (0.05 for 5%), but `main.py` has a manual guard for `TARGET_NET_ROE >= 1.0`. This suggests a recurring user error pattern.
- **Impact:** Incorrect risk calculation. If a user enters `5` instead of `0.05`, the bot might attempt to risk 500% of equity or target impossible profits.
- **Recommendation:** Implement a strict configuration validator/parser that enforces types and ranges, or move to a standard percentage format (0-100) and convert internally.

### [CS-004] Hardcoded Initial Equity in Comparison Suite
- **Location:** `compare.py`, `variant_runner`
- **Description:** `INITIAL_EQUITY` is imported from `config.py` and used to reset the simulator balance. However, if a variant overrides `INITIAL_EQUITY`, the `DataCoordinator` (which warms up first) might use the baseline value while the runners use the override.
- **Impact:** Inconsistent starting points for A/B tests if equity-related parameters are being tested.
- **Recommendation:** Pass the intended `INITIAL_EQUITY` explicitly from the `DataCoordinator` to the `VariantRunner` to ensure all subprocesses start with identical capital.

### [CS-005] Dead Code: LearningModel Weight Updates
- **Location:** `models.py`, `LearningModel.lr`
- **Description:** `lr` (learning rate) is set to `0.0`. The training logic in `train_on_tick` still executes math operations that effectively do nothing.
- **Impact:** Technical debt and minor performance waste.
- **Recommendation:** If online learning is "Not yet" (per code comments), the training loop should be gated by a boolean `USE_LEARNING` to avoid unnecessary feature lookups and math.

## 2. Technical Analysis Tools

### [TA-001] Lack of Smoothing in RSI and ATR
- **Location:** `ta/indicators/rsi.py`, `ta/indicators/atr.py`
- **Description:** The RSI implementation uses a simple average of gains/losses over the period (`avg_gain = gains / period`). Standard RSI (Wilder’s) uses exponential smoothing. Similarly, ATR uses a simple average of True Range.
- **Impact:** The indicators are significantly more "jittery" than standard implementations, leading to premature signals or "noise" entries that don't reflect true momentum.
- **Recommendation:** Replace simple averages with Wilder’s Smoothing (WMA-style) or EMA-based averages to match industry standards and improve signal reliability.

### [TA-002] Look-ahead Bias in Pattern Detection
- **Location:** `simulator.py`, `get_features` (Line 158)
- **Description:** The feature calculation uses the *current* developing candle (`ohlcv[-1]`) for patterns like FVG, OB, and Structure.
- **Impact:** **Repainting.** A signal might trigger because the mid-candle price created an FVG, but by the time the candle closes, the gap is filled. The backtester/simulator sees a "perfect" entry that wouldn't exist in a close-confirmed environment.
- **Recommendation:** Most structural patterns (BOS, MSS, FVG) should only be detected on *closed* candles (`ohlcv[-2]`). Only price-action triggers (Liquidity Sweeps, Imbalance) should use the live candle.

### [TA-003] DRT Sensitivity and Frequency Mismatch
- **Location:** `ta/patterns/drt.py`
- **Description:** DRT calculates a linear regression slope over 20 points. When run on a 1m timeframe but updated every 0.2s tick, the "slope" is extremely sensitive to micro-movements.
- **Impact:** The `TREND_STRENGTH_MIN` filter might oscillate rapidly, causing the bot to "stutter" at entry points.
- **Recommendation:** DRT should be calculated on a fixed-interval OHLCV (e.g., the last 20 1-minute closes) rather than being recalculated on every tick using the developing candle's mid-price as the 20th point.

### [TA-004] Simplified POI Confluence
- **Location:** `ta/patterns/poi.py`
- **Description:** Confluence is currently a binary check: if price is within 0.2% of a level, it's "active." It does not weight the *quality* of the level (e.g., a 4H OB vs a 1m FVG).
- **Impact:** Low-quality levels trigger the same "POI bonus" as high-probability institutional zones.
- **Recommendation:** Implement a weighted scoring system where HTF levels (4H/1D) provide significantly more confluence weight than LTF levels.

### [TA-005] Session High/Low Precision
- **Location:** `ta/patterns/sessions.py`
- **Description:** The session tracker iterates through all provided OHLCV to find H/L. If the bot restarts mid-session, it only knows the H/L of the candles it fetched during `warm_up` (default 100-500).
- **Impact:** If the session high occurred 600 candles ago, the bot will miss it, leading to incorrect "Liquidity Sweep" detections.
- **Recommendation:** Session extremes should be fetched explicitly from the exchange or persisted in the `market_data.db` to ensure continuity across restarts.
