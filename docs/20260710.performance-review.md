## Signal-to-Trade Conversion Analysis

- **Logged Setup Setups**: setup events are successfully detected and recorded in `docs/temp/` metrics logs.
- **Pipeline Droppage Point**: The drop-off in live mode was traced entirely to the limit order timeout/chase omission:
  - Once a limit entry order was placed, it was never registered in the `pending_orders` queue.
  - Since it wasn't tracked, it was never checked for timeout cancellations.
  - The asset remained permanently locked under `pending_entries`, silently suppressing all subsequent entry setups for that asset.
- **Resolution Impact**: Registering limit entries inside the timeout queue guarantees that unfilled limits are canceled after `LIMIT_CHASE_TIMEOUT` (10s), instantly releasing the asset lock and maintaining consistent compounding frequency.

## Leverage, Liquidation Protection, and Exit Trigger Order Performance Analysis

- **Leverage Performance**:
  - Previously, all trades opened at 10x leverage because the bot was not configuring leverage on the exchange.
  - With `/api/v2/mix/account/set-leverage` and `/api/v2/mix/account/set-margin-mode`, the system now enforces the maximum available leverage (up to 125x depending on asset limits) and places the position in an Isolated Margin state.
  - This perfectly aligns with our high-frequency rapid compounding target of over 100M USDT from a small starting balance.

- **Liquidation Protection (Issue D)**:
  - Enforcing `RISK_PER_TRADE` means that if a position hits Stop Loss, that is the absolute maximum amount that can be lost.
  - To guarantee that liquidation does not happen before the Stop Loss is hit, we dynamically calculate and set leverage as `min(max_leverage, max_safe_leverage)` where `max_safe_leverage = int(0.9 / (abs(price - sl_price) / price))`.
  - This mathematically guarantees that the liquidation price is wider than the Stop Loss price, ensuring that the Stop Loss is hit first and the position is never prematurely liquidated.

- **Trigger Order Sync Performance**:
  - Standard presets inside the order placement call only support a single target.
  - By adding our position-audit sync loop in `_sync_exchange_state`, the engine fetches pending plan orders and compares them with the target positions.
  - If any TP1 triggers are missing on position creation or after restarts, they are automatically placed as partial TP triggers on-exchange.
  - The position's full stop loss remains safely embedded in the entry call as an order preset, providing absolute instant risk coverage, while the secondary targets are seamlessly posted via plan orders.

## Backtest vs. Live Performance Parity

- **Look-Ahead Bias Resolution**:
  - Previously, `backtest.py` was synchronizing multi-timeframe candles (15m, 1H, 4H, etc.) at the beginning of their periods, resulting in up to 15-minute, 1-hour, or 4-hour look-ahead data visibility for strategies.
  - We implemented perfect candle closed alignment: a candle of timeframe `t` is only pre-populated or synchronized into the active history once its period is fully ended (`ts + TF_SECONDS[t] <= current_ts`).
  - This eliminates all look-ahead bias in indicators and signals, ensuring that backtest performance reflects real-world market constraints exactly.

- **Mode and Credential Independence**:
  - The backtest engine now instantiates the core trading engine forced to `mode="paper"`, ensuring it runs perfectly in simulation mode regardless of `.env` configuration (e.g. `MODE="live"` or `MODE="demo"`).
  - Hardened client public requests to work without private keys, enabling any user to run backtests, download data, and evaluate strategies seamlessly.

- **Multi-Asset Portfolio Capital Pooling (Issue E)**:
  - We refactored `backtest.py` to support `run_backtest_portfolio()`.
  - All specified assets are simulated simultaneously on a single, shared chronological timeline.
  - Sizing for each trade automatically adapts to actual remaining shared available margin, and portfolio-wide concurrency limits (`MAX_CONCURRENT_POSITIONS`) are respected globally.
  - This matches live trading capital-sharing behavior with 100% precision.

- **Cache Isolation & Swing Parity (Issue F)**:
  - Fixed a critical swing high/low cache key fingerprint collision inside `ta/patterns/swings.py` where different assets evaluated in the same tick shared identical cached swing targets, corrupting the take-profit / exit prices.
  - Implemented absolute close-price based cache key signatures, delivering 100% target and exit pricing parity.

- **Zero-Width Fee Trap Protection (Issue G)**:
  - Implemented a mandatory minimum Stop Loss distance check of **0.1%** of entry price in all three core strategies, preventing high-frequency fee drain trades where FVG boundaries are too close.
