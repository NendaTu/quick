# Technical Audit Report - 2026-07-08

## Executive Summary
This audit was performed to identify and resolve blockers preventing the trading system from executing trades in Live/Demo modes on the Bitget exchange. The primary blockers were an unhandled `KeyError` in the trading loop and repeated API authentication failures due to time synchronization drift. Both have been resolved. Further optimizations for signal logging and strategy state management have been identified.

---

## Confirmed Issues & Resolutions

### Issue 1: `KeyError: 'btc_confluence'` (CRITICAL)
- **Location**: `engine/core.py` line 780
- **Description**: The engine attempted to access `signal["btc_confluence"]` directly. Strategies following the Mustafa suite often did not include this key, or included it under different conditions, causing the entire trading loop for that tick to crash.
- **Severity**: Critical (Blocker)
- **Fix**: Replaced direct key access with `.get()` and provided sensible defaults for `qty`, `entry_price`, `stop_price`, `exit_price`, and `btc_confluence`.
- **Status**: **RESOLVED**

### 6. Redundant Historical Data Downloads
- **Location**: `database.py` in `get_data_gaps`
- **Finding**: The gap detection logic used a block-count heuristic. If a range was missing even one candle, the heuristic might return the entire range as a "gap", causing the downloader to re-acquire data already in the database.
- **Severity**: Medium
- **Fix**: Replaced the heuristic with a precise timestamp-comparison scan. The new logic identifies exact missing segments, ensuring zero redundant API calls for already-acquired data.
- **Status**: **RESOLVED**

### 7. Downloader Coverage Reporting
- **Location**: `tools/downloader.py`
- **Finding**: The downloader lacked visibility into existing data coverage, making it difficult to verify if historical ranges were truly complete.
- **Fix**: Implemented `report_coverage()` which prints a detailed percentage-based coverage table for all assets before starting acquisition.
- **Status**: **RESOLVED**

### 8. Proactive Rate Limiting
- **Location**: `bitget_client.py` and across all REST-calling engines.
- **Finding**: High RPS during initial data acquisition or high-frequency trade evaluation was triggering 429 errors, disrupting the bot's flow.
- **Fix**: Implemented a centralized `RateLimiter` with a "98% safety cap" (target: 19.6 RPS). This limiter is shared between clients in `BitgetExchange` to ensure cumulative REST traffic never breaches exchange limits.
- **Status**: **RESOLVED**

### Issue 2: `code: 40008` Request Timestamp Expired (HIGH)
- **Location**: `bitget_client.py` and `engine/exchanges/bitget.py`
- **Description**: Bitget V2 API requires request timestamps to be within a tight window of server time. Local clock drift caused requests to be rejected. The existing `sync_time` failed because it didn't handle the V2 response format (dictionary vs scalar).
- **Severity**: High
- **Fix**:
    1. Updated `BitGetClient.sync_time` to correctly parse `serverTime` from the V2 JSON response.
    2. Implemented `_time_sync_poller` in `BitgetExchange` to refresh the offset every 5 minutes.
- **Status**: **RESOLVED**

### Issue 3: WebSocket Reconnection Storm (HIGH)
- **Location**: `bitget_client.py` (`BitGetWSClient`)
- **Description**: Frequent disconnects were triggered by authentication failures (40008) and state sync errors.
- **Severity**: High
- **Root Cause Analysis**: Time drift (Issue 2) was the primary driver of authentication failures during WS login.
- **Status**: **MITIGATED** (Resolved via Issue 2 fix)

### Issue 4: Signal Log Not Written in Live/Paper (HIGH)
- **Location**: `engine/core.py`
- **Description**: The `metrics-log.txt` was only being written inside `_report_entry`, which only occurs after a trade is successfully filled. Signal evaluations that didn't lead to trades were never logged.
- **Severity**: High
- **Fix**: Moved the call to `_write_metrics_log` into the main `_trading_loop` in `engine/core.py`, ensuring every signal evaluation is captured.
- **Status**: **RESOLVED**

## Technical Audit Findings

### 1. Strategy State Machine Deadlocks
- **Location**: `strategies/sweeps/killzone/killzone_sweep.1.mustafa.py` and `strategies/sweeps/range/range_sweep_ATR.1.mustafa.py`
- **Finding**: After a trade is successfully triggered, the state is set to `COMPLETED`. However, there is no logic to transition back to `IDLE` for the same session/range. This prevents the strategy from taking more than one trade per asset per session, even if another valid setup occurs.
- **Severity**: Medium
- **Fix**: Implemented a 1-hour cooldown reset in all sweep strategies. If state is `COMPLETED` and > 1 hour has passed since the trigger, the state reverts to `IDLE`.
- **Status**: **RESOLVED**

### 2. Look-ahead Bias in FVG Signal evaluation
- **Location**: `ta/patterns/fvg.py` in `get_signal`
- **Finding**: The `get_signal` function used by the legacy confluence chain uses `ohlcv[-1]`, which is the currently forming candle. If a signal is emitted based on an unclosed candle's wick, the signal might "repaint" or disappear if the candle closes differently.
- **Severity**: Medium
- **Fix**: Updated `get_signal` in `ta/patterns/fvg.py` to use `ohlcv[:-1]` (only closed candles).
- **Status**: **RESOLVED**

### 3. Activity-Based Optimization Gate
- **Location**: `engine/core.py` line 748
- **Finding**: `if sym == BTC_SYMBOL or has_pos or (now - last_act < 1.0):`
- **Description**: The engine skips feature calculation for assets that haven't had a WebSocket update in > 1 second. For low-liquidity assets, this might cause the bot to miss the very first tick of a volatile move that could have triggered a signal.
- **Severity**: Low
- **Fix**: Increased the timeout from 1.0s to 10.0s to allow more tolerance for sporadic WebSocket updates.
- **Status**: **RESOLVED**

### 4. Brittle `literal_eval` in Strategy State
- **Location**: `strategies/base_strategy.py`
- **Finding**: Strategies were performing manual `ast.literal_eval` on strings from the DB.
- **Severity**: Low
- **Fix**: Centralized safe state parsing in `JBaseStrategy.get_state()`.
- **Status**: **RESOLVED**

### 5. `tp1_qty` Potential Zero-Rounding
- **Location**: `strategies/sweeps/killzone/killzone_sweep.1.mustafa.py`
- **Finding**: `tp1_qty = round(qty * self.params["tp1_qty_ratio"], qty_place)`. For assets with very small minimum quantities (e.g. 0.001), a 50% split might round to 0.001 or 0.000, causing order rejection.
- **Severity**: Low
- **Fix**: Added minimum tick size check for `tp1_qty`. If the split quantity is less than one tick, the split is disabled (tp1_qty set to 0).
- **Status**: **RESOLVED**

### 6. Strategy "Warm Start" Gap (Historical Catch-up)
- **Location**: Mustafa Sweep Strategies (`strategies/sweeps/`)
- **Finding**: Strategies were only identifying setup milestones (Sweeps, BOS, FVG) in real-time price action after bot startup. Any setups initiated before startup were ignored, causing missed opportunities during the first few hours of operation.
- **Fix**: Implemented a "Fast-Forward" mechanism. On startup, strategies scan up to 8 hours of 15m and 1m history to identify sequences already in progress, allowing the bot to enter a trade-ready state immediately.
- **Status**: **RESOLVED**

## Summary of Trading Performance Observations (Issue 5)
1. **Asset Discovery**: Live run only found 70 assets. `ASSETS_COUNT` is 250. This is likely due to the `usdtVolume` filter or Bitget's API response at the time of run. Fewer assets = fewer signals.
2. **KeyError impact**: The KeyError was crashing the `_trading_loop` task. In `asyncio`, if a task crashes and isn't handled, it might stop running entirely or wait for the next exception to be logged. This explains why zero trades reached the exchange despite signals being logged earlier.
3. **Parity Check**: Backtest uses "clean" historical data. Live mode deals with WebSocket gaps and jitter. The state machines for sweeps are highly sensitive to "wick-only" touches which might be filtered differently in live vs historical data.
